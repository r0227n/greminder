# 通知タップからタスク詳細への遷移

## 実装

既存の `NotificationPlanner.key` を通知とタスクの対応付けに使用する。キーにはアカウントのスコープ、リストID、リモートID（未保存時はローカルID）が含まれる。通知生成・権限・予約・表示は既存の `LocalNotificationSystem` を使用する。

通常通知には対応キーを `userInfo` に格納する。以前に予約・配信された通知についても、既存の通知識別子から同じキーを復元する。デバッグ通知は画面で選択したタスクのキーを同じ生成処理へ渡す。

[Appleのdelegate登録要件](https://developer.apple.com/documentation/usernotifications/unusernotificationcenter/delegate)に合わせ、アプリの起動完了前に通知delegateを登録する。タップはバッファに保持し、画面の購読開始・タスクの読み込み・表示中のシートの終了を待ってから、既存の詳細表示Actionで対象タスクを開く。削除済み・別アカウントの場合は誤ったタスクを開かず、見つからない旨を表示する。読み込み失敗時はタップを保持して再読み込み時に再試行する。

## Simulatorでの実操作確認（2026-09-15）

iPhone 17 Pro Max / iOS 26.2、Debugビルド、保存済みサンプルデータで実施。デバッグ画面からタスクを選択し、既存の通知基盤で5秒後のローカル通知を予約した。OSの通知バナーを実際にタップして確認しており、内部ActionやURLを直接呼んで代用していない。

| アプリの状態 | 操作と確認結果 | 証跡 |
| --- | --- | --- |
| フォアグラウンド | デバッグ画面の表示中に「コーヒー豆を買う」のバナーをタップ。デバッグ画面が閉じ、「買い物」の該当タスク詳細が開いた。 | [画面](notification-navigation-foreground.jpg) |
| バックグラウンド | 「本を返す」を予約してホームへ移動。バナーをタップすると「プライベート」の該当タスク詳細が開いた。プロセスIDは起動時と同じ92663で、クラッシュ・再起動なし。 | [画面](notification-navigation-background.jpg) |
| 終了状態 | 「来週の打ち合わせを準備する」を予約し、Simulatorの停止操作でアプリプロセスを終了。通知をタップして起動し、読み込み後に「仕事」の該当タスク詳細が開いた。新しいプロセスID93952を確認。 | [画面](notification-navigation-terminated.jpg) |

検証中に、async版通知応答delegateの完了処理がバックグラウンドスレッドで実行され、UIKitの状態復元で `Call must be made on main thread` が発生する問題を検出した。completion handler版に変更し、通知イベントの配信と完了処理をMainActor上で実行するよう修正した後、上記3状態をすべて再確認した。

## ログインと編集取消の回帰確認（2026-09-17）

iPhone 17 Pro Max / iOS 26.2のDebugビルドを`--design-preview`で起動し、保存済みGoogleセッションを使用せず、メモリ内のサンプルタスクで実施した。デバッグ画面から実際の`LocalNotificationSystem.schedule`で5秒後・15秒後の通知を予約し、OSバナーをタップした。遷移Actionの直接注入は行っていない。

| ケース | 操作と確認結果 | 証跡 |
| --- | --- | --- |
| 未ログインでサンプル通知をタップ | サンプルホームをオフにし、「本を返す」を予約。ログイン画面でバナーをタップしてもログインボタンは有効。デバッグ画面で「保留なし」「編集中のタスク、なし」を確認。 | [ログイン画面](notification-signed-out.jpg)、[状態](notification-signed-out-state.jpg) |
| 不正な入力中に通知をタップ | 新規タスクのタイトルにキーボード操作で1,025文字入力。「本を返す」のバナーをタップすると入力上限エラーになり、入力を保持。デバッグ画面に「保留中」「編集中のタスク、あり」、文字数1,025を表示。 | [保留状態](notification-invalid-draft.jpg) |
| 編集取消で通知先へ進む | 上記状態から「編集を取り消して閉じる」を1回押す。シート終了後に「プライベート」リストの「本を返す」詳細を表示。取消は通常のインライン編集のEscと同じ`cancelEditor`を使用。 | [通知先の詳細](notification-cancel-resumed.jpg) |
| ログイン画面とホームの往復後 | サンプル表示をオフ→オンにした後、上記の入力・通知・取消を繰り返し、最後まで遷移することを確認。 | 上記の保留状態・詳細画面 |

打鍵中に、条件分岐を持つルート`Group`で画面を切り替えると通知購読タスクが終了する経路も見つかった。ルートを`ZStack`にし、画面切替の外側にあるライフサイクルと通知購読を維持した。デバッグ画面内の`dismiss()`はNavigationStackの1段だけを戻すため、取消ボタンではシート表示状態を閉じるよう修正して再確認した。

取消後に元の入力エラーが通知先の詳細に残る点も修正した。取り消す入力と一致する検証エラーだけを消し、保存失敗などは保持する。最終ビルド（プロセスID28342）で1,025文字入力→OS通知タップ→取消を再実行し、通知先タイトル「本を返す」と入力エラー表示がないことを確認した。

この追加確認はiOS Simulatorのローカル通知と入力・取消操作を対象とする。実Google OAuthの完了、実機、macOSのEscキー操作は今回の打鍵対象外。認証成功・失敗と取消Actionは自動テストで検証する。

### Swift Testing

打鍵確認完了後、[Apple Swift Testing](https://developer.apple.com/documentation/testing)の`@Suite` / `@Test` / `#expect` / `#require`を使用して`Tests/NotificationRegressionTests.swift`を追加した。

- 正常系：ログイン成功後の保留通知の再開、明示的なサンプル表示、正常な編集中データの保存と遷移、編集取消後の遷移、共通通知の日時・タスクキー。
- 異常系：未ログインでのサンプル通知、認証中の読込失敗と再試行、タイトル1,025文字・メモ8,193文字、新規/既存のインライン編集、詳細画面の不正入力の保護、削除済み・別アカウント・不正な通知。
- 既存の通知遷移テストはサンプル表示を明示して継続。削除したデバッグ専用通知クラスのテストは、通常通知と手動通知が使用する共通生成処理のテストに置き換えた。

最終結果：`swift test --skip-update`成功。Swift Testingは12テスト（パラメーター展開後19ケース）すべて成功。既存XCTestは94件中93件成功、任意の実音声テスト1件スキップ、失敗0。iOS Simulatorビルド・起動、`bash scripts/quality.sh check`（翻訳306キー、SwiftFormat、SwiftLint違反0）、`git diff --check`も成功した。
