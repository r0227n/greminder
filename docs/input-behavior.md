# 純正リマインダーの入力観察

2026-09-13、ユーザー指定のmacOSリマインダーアプリをCuaで実際に操作しました。既存データのタイトルを実装用フィクスチャへコピーしていません。

| 操作 | 観察結果 | greminder |
|---|---|---|
| Macの余白を1回クリック | 選択・入力を解除 | 編集を確定して入力行を閉じる |
| Macの余白をダブルクリック | 新しい空欄行にフォーカス | 同じ動作 |
| タイトル入力後Enter | 保存し、直後に空欄行 | 同じ動作。保存は直列キューで進める |
| 次の空欄でEnter | 空タスクを作らず連続入力終了 | 同じ動作 |
| 既存タイトルを編集してEnter | 編集した行の直下に新規行 | 同じ動作 |
| 既存タスク選択中 | メモ・日付などを一覧内で編集 | タイトル・メモ・予定日を提供 |
| iOSの余白タップ | ユーザー指定による操作方針 | 新規行へフォーカス |

検証で追加した識別可能な2件のみ削除し、元のアクティブ件数に戻したことを確認しました。2件は純正リマインダーの「最近削除した項目」に残っています。

実装上、Enter直後にSwiftUIのフォーカスを変更するだけでは、AppKitが破棄中のTextFieldへフォーカスを戻す問題がありました。新しい入力行の `.task(id:)` でマウント後にフォーカスを要求します。

通常のタイトル入力はネイティブTextFieldの `onSubmit` を使い、独自のReturnキー監視でIMEの変換確定を奪わない構成です。Macでは日本語の貼り付けからEnterで次の行に続けて入力できることを確認しました。iPhone 17 Pro Max / iOS 26.2 Simulatorでは、かなキーボードの「あ」を入力し、最初の「次へ」で変換確定、続く「次へ」で保存して新規行を作成、その行へタップし直さずかな入力できることを確認しました。長い連文節変換は別途確認が必要です。
